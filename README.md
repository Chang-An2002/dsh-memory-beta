# dsh-memory-beta

给 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）加一层**长期记忆**与**带来源的知识库召回**。

## 它解决什么问题

DSH 原生的检索是 `glob` / `grep`：**精确匹配**。你想不起来某个决定写在哪个文件、或者只记得"大概是关于存储选型的那段"，它就帮不上忙。而 `web_search` 查的是外网，不是你的资料。

同时，DSH 每次会话都是新的：你上一周说过的偏好、这个项目定下来的约定，下次对话它不知道。

这个插件补上这两件事：

| 能力 | 说明 |
|---|---|
| **`kb_search`** | 在你自己的工作区里做混合召回，返回**带 `路径:行号` 引用**的片段；证据不足时明确说"没找到"，而不是编 |
| **`memory`** | 跨会话的长期记忆，分**用户级**（跨所有项目）与**项目级**（仅本项目），**存成你能直接打开改的 Markdown** |
| 记忆自动注入 | 每次请求都把长期记忆带进系统提示词，所以新会话开局就知道你是谁、这个项目的约定是什么 |

## 设计上刻意的三个选择

**1. 记忆是人类可读的 Markdown，不是数据库。**

```markdown
<!-- dsh-memory:project v1 -->
# 项目长期记忆：my-project

- `决定.存储` 记忆载体用 Markdown + JSON，不用 SQLite：必须可人工审阅与 git 管理。 <!-- @2026-10-09 src=model -->
- `技术栈` 纯 ESM JavaScript，零运行时依赖。 <!-- @2026-10-09 src=model -->

<!-- user-notes -->
（这里是你自己的自留地，插件原样保留、不解析、不重排）
```

理由：记忆系统最怕的不是"存不下"，而是**模型偷偷记错了还一路传下去**。Markdown 让你用记事本就能纠正一条，不需要工具、不需要 SQL。它也天然进 git，团队可以共享项目级记忆。

**2. 索引不是事实源。** 原始文档始终在工作区里，索引只是它的可检索投影。删掉索引不丢任何信息，只是下次检索前要重建。**索引里也没有你的原文副本之外的任何东西。**

**3. 零运行时依赖。** 不引入 `node:sqlite`、不上原生模块、不下载模型。装完即用，这也是它能跨平台的原因。

## 安装

插件通过 DSH 自带的插件管理器安装。**装完如果没看到效果，先重启一次客户端**——新版工具通常热生效，但提示词注入部分在部分场景需要重启。

### 桌面客户端（Electron）

桌面端读的是 `desktop` profile，而 `dsh plugin` 命令行**按设计拒绝**操作它。正确方式是在桌面客户端的会话里直接说：

> 把 dsh-memory-beta 装上

它会调用内置的 `plugin_manager` 工具，用客户端自带的 pnpm 在当前 profile 里装好并写入 `dsh.profile.bundles`。

### Web（`dsh web`）

```bash
# 从 GitHub 安装
dsh plugin --profile web add github:Chang-An2002/dsh-memory-beta

# 从本地目录安装（开发时用，改动立即生效）
dsh plugin --profile web add link:D:\path\to\dsh-memory-beta
```

安装后重启 `dsh web` 并刷新浏览器。

### 手动安装（不依赖插件管理器）

在 profile 目录（`~/.dsh/profiles/<profile>/`）里：

```bash
pnpm add github:Chang-An2002/dsh-memory-beta
```

然后在该 profile 的 `package.json` 的 `dsh.profile.bundles` 数组里加上 `"dsh-memory-beta"`。

## 使用

### 五个工具

| 工具 | 什么时候用 |
|---|---|
| `kb_index` | 想让索引更新时手动跑一次。**不是必须的前置步骤**——`kb_search` 会自己检测过期并重建。增量更新，重复跑很便宜 |
| `kb_search` | 答案应该来自你自己的资料时。返回带引用的片段，或明确告诉你"没找到" |
| `kb_stats` | 想知道"它到底索引了什么文件"、以及索引有没有过期时。**只报告、不改动索引**，所以回答依据可以原样核对 |
| `memory` | 记下稳定成立的事：`action` 取 `read`/`write`/`forget`，`scope` 取 `user`/`project` |
| `memory_search` | 记忆条数变多后按内容检索 |

典型的一轮对话：

```
你：这个项目为什么不用 SQLite 存记忆？
（模型调用 kb_search）
模型：按 docs/DESIGN.md:132-150 的记录，有三个理由：可审阅、git 友好、零依赖……
```

如果资料里确实没有：

```
你：这个项目支持 PostgreSQL 吗？
模型：我在你的资料里没找到相关内容（检索范围：工作区已索引文档）。
```

**注意最后这一句**：插件会明确指示模型不要用训练知识把这个空缺补上。因为此刻你要的是你资料的答案，不是通用知识。

### 索引不会悄悄过期

改了文档却忘了重新索引，检索到的就是旧内容——而且**它不会报错，是静默答错**。这是知识库类工具最危险的失败模式。

所以每次 `kb_search` 之前会先做一次过期检测（实测：55 个文件的工作区约 0.5 ms，见下），发现变化就**先重建索引再检索**，并在结果里如实写明：

```
注意：工作区自上次索引后有变化（改动 1 个）——docs/deploy.md。
已自动重新索引后再回答。

检索：插件怎么安装
...
```

检测分两级，为的是**既不漏也不误报**：

1. 先比文件的修改时间（`mtime`）——绝大多数文件在这一步就排除了，不读内容；
2. 只有时间变了的文件才重新读盘算内容指纹。指纹一致就判定为**没变**。

第 2 步不能省。`git checkout`、切换分支、格式化保存、复制文件都会改 `mtime` 但内容没变；只看时间的话，这些操作全会被误报成"过期"，然后触发一次毫无必要的大规模重建。

如果不想让插件自动碰索引，把它关掉：`config: { autoReindex: false }`。此时检索仍会提醒你索引过期，但不会自己动手。

**`kb_stats` 也做同样的检测，但不重建。** 两个工具对"索引新不新鲜"必须给出一致结论——一个报"已索引 12 个文件"、另一个报"有 3 个文件变了"，用户就没法相信任何一个数字。但 `kb_stats` 的定位是"核对依据"的只读工具，偷偷改掉它正在报告的东西会让人没法信任这份报告，所以它只如实说明：

```
注意：工作区自上次索引后有变化（改动 1 个）——docs/deploy.md。
下面报告的是索引里的旧数据。

工作区：...
```

换句话说：**过期检测两边一致，重新索引只发生在检索路径上。**

### 配置

写在 profile 的 `cordis.patch.yml` 里：

```yaml
- id: dsh-memory-beta
  name: dsh-memory-beta
  config:
    maxPassages: 6          # kb_search 默认返回的片段数
    injectMemory: true      # 是否把长期记忆注入系统提示词
    maxInjectedEntries: 40  # 注入的条数上限
    maxInjectedChars: 3000  # 注入的字符预算
    autoReindex: true       # 检索前发现索引过期时，是否自动重建（关掉则只提醒）
```

## 数据存在哪

全部在 `$DSH_HOME`（默认 `~/.dsh`）之下，**不放在插件目录里**（插件目录可能被包管理器清理）：

```
~/.dsh/memory/
  user.longterm.md                                    用户级长期记忆（跨所有项目）
  projects/<工作区键>.longterm.md                      项目级长期记忆
  index/<工作区键>.json                                工作区检索索引（可随时删除重建）
```

`<工作区键>` 形如 `my-project--f07f7b24`：前面是路径摘要（方便你认出是哪个项目），后面是短哈希（保证唯一）。**它会剥掉你的家目录前缀**，所以键里不会出现你的用户名。

工作区索引只包含 DSH 配置里的当前工作区，不会扫到别处。

## 隐私边界

这是你该知道清楚的几件事：

- **不上传任何东西。** 没有网络请求，没有遥测，"记忆"全部是本机文件。
- **不索引的内容**：`node_modules`、`.git`、`dist`/`build`/`target` 等构建目录、常见锁文件、超过 512 KB 的文件、二进制文件（含 NUL 字节或非 UTF-8）、**符号链接**（避免一个软链把工作区之外的文件悄悄纳入索引）。
- **不参与检索**：工作区里的 `.dsh-memory/` 目录（团队共享记忆用）本身不被索引，避免"记忆污染知识库"。
- **可审计**：`kb_stats` 会列出所有被索引的文件；索引文件是纯 JSON，你可以直接打开看。
- **插件不会自己删你的记忆**。删除只发生在你或模型显式调用 `memory action=forget` 时，且会回报删掉了什么。

## 已知限制

我宁可写清楚，也不想让你踩到才发现。

### 检索质量

- **目前只有 BM25 稀疏召回，没有语义召回。** 这意味着：你问"怎么找出基因组之间的差异"，而文档标题写的是"变异检测流程"——**两者没有共同词，召回不到**。这是词面匹配的固有限制。
  - 代码和文档场景下这个限制没有听起来那么严重：标识符、路径、报错串都是精确 token，正是 BM25 的甜点区。
  - 架构上已经为语义召回留好位置：融合层从第一天就是多路 RRF，加入 embedding 是"多一路输入"，不需要重写编排。
- **没有精排（rerank）。** 参考实现用的本地 cross-encoder 需要约 5 GB 常驻内存、单次精排 8–17 秒，与"装完即用"的定位冲突。
- **中文分词是字符二元组 + 停用词表**，不是真正的中文分词器。这是为避免引入 jieba 之类的依赖而做的取舍，在多数技术文档上够用，但对长句和口语化表达不如专业分词。
- **单次检索的延迟随语料规模线性增长**（内存 BM25，每次查询全量打分）。几千到几万片段是亚秒级；更大的语料需要换倒排索引。

### 记忆

- **记忆不会自动整理。** 插件不会自己去重、合并、判断矛盾，也不会主动忘掉过时的条目。同一件事用不同 key 记两次就是两条。目前靠模型在写入前先读一次，以及你自己的判断。
- **`src=model` / `src=human` 只是标记，还没影响行为。** 我区分了来源，但还没有"模型推断的内容降权"之类的机制。
- **注入有预算**：默认最多 40 条、3000 字符。超出时不会静默丢弃，会告诉模型"还有更多，可用 `memory_search` 查"，但**模型不一定每次都会去查**。
- **模型可能记错东西。** 这是本设计里最重要的一条：请把记忆文件当成"待审阅的笔记"而不是"事实"。定期的做法是打开 `~/.dsh/memory/user.longterm.md` 看一眼，用 `memory action=forget` 或直接编辑文件纠正。

### 工程

- **团队共享记忆尚未实现。** 设计上计划在工作区放 `.dsh-memory/project.md` 供提交进 git，插件发现即读取且**不自动写入**（把"可提交"与"只该自己看"从物理上分开）。目前这部分还没做，记忆只存在 `~/.dsh` 下。
- **索引过期是"检索时检测"，不是"文件一变就重建"。** 没有文件监听：变化要等到下一次 `kb_search` 才会被发现（并自动重建）。所以单次检索的结果按**检索那一刻**的工作区算，这点是准的；但如果你在两次检索之间改了文档却没有再检索，插件不会主动知道。检测策略见上面「索引不会悄悄过期」。
- **自动重建会改写索引文件**。它不动你的文档，索引本身也只是可重建的派生物；但索引默认放在 `~/.dsh` 下，一般不在同步盘里，所以通常不会带来额外同步流量。
- **索引在内存里全量驻留**。语料很大时（十万级片段）启动与内存开销会明显上升。
- **跨平台只在 Windows 上实测过**。代码里没有平台特定假设，但 Linux/macOS 未验证。
- **`kb_search` 一次只处理一个查询。** 复合问题（"A 和 B 分别是什么关系"）目前靠模型自己拆成多次调用，插件内置的查询分解与多跳编排**没有移植**——参考实现那部分逻辑（`query_planner.py`、`wiki_router.py`）深度耦合于某个特定机器人的领域（Wiki 路由、群聊身份），直接搬过来只会带来负担。这是有意的删减，不是遗漏。

## 卸载

```bash
dsh plugin --profile web remove dsh-memory-beta
```

桌面端在插件页面里取消选择，或让 DSH 自己卸载。

**记忆文件不会被自动删除**——它们是你的数据。要一并清理：

```bash
rm -rf ~/.dsh/memory
```

## 开发

```bash
git clone https://github.com/Chang-An2002/dsh-memory-beta
cd dsh-memory-beta
node --test test/          # 全部测试
```

测试按层组织，每层可独立运行：

| 文件 | 覆盖 |
|---|---|
| `test/retrieval.test.js` | 分词、BM25、RRF 融合 |
| `test/chunking.test.js` | 结构感知切分、标题路径、行号 |
| `test/memory.test.js` | 路径与工作区键、记忆文件读写、与人工编辑共存 |
| `test/evidence.test.js` | 充分性判定、预算裁剪、来源标注 |
| `test/index.test.js` | 文件发现、增量索引、**过期检测**、检索编排、引用可核对 |
| `test/plugin.test.js` | 工具注册、**宿主契约（`Config` schema / 参数编译 / 段落 order）**、自动重索引、记忆注入、失败隔离 |

> 单元测试用的是**假桩宿主**，它测不出"宿主怎么读我们的导出"这类契约问题。改动 `Config`、`inject`、`output`、`parameters`、提示词段落或变量名时，务必也启动一次真实 DSH 验证——这个插件曾经在 62 项自检全绿的情况下**一次都没能激活**。

架构与移植依据见 [DESIGN.md](DESIGN.md)。

## 这个插件的来路

它的检索与记忆设计来自另一个项目 **ArkSeek**（Python，QQ 机器人，四层记忆 + 混合召回 + 可靠性兜底），那个项目在真实语料和真实群聊上迭代过多轮。这里移植的是它的**设计判断**，不是代码：运行时用零依赖 JavaScript 重写，因为参考实现依赖约 6.6 GB 的模型、需要 8 GB 内存、单次精排 8–17 秒——一个"装完即用"的插件不该有这种前置条件。

哪些判断被继承、哪些被有意砍掉、依据是什么，都记在 [DESIGN.md](DESIGN.md) 里。
